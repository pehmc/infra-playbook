数据库：
关系模型适合多对一关系，强 Schema、频繁 Join。原因是二级索引、事务、外键约束成熟。在 EDC 中，这对应的是核心交易数据：订单、支付、账务、库存、客户主数据。这些数据的共同特征是正确性要求极高，业务规则频繁变化，需要 Schema 约束来保护数据质量。EDC 对这类数据的供给方式是：作为一级标准服务提供，统一版本、统一运维、统一备份恢复策略。不允许业务团队自建关系数据库，因为那会导致版本碎片化、备份策略不一致、安全策略不统一，最终在故障切换和审计时付出代价。

文档模型适合数据自包含、文档间关系稀少的场景。原因是嵌套存储，局部性好。在 EDC 中，这对应的是半结构化数据：内容管理、用户配置、商品详情、日志聚合。这些数据的共同特征是查询以单个文档为单位，跨文档关联少，Schema 灵活。EDC 对这类数据的供给方式是：作为可选服务提供，但必须有明确的使用场景审批。因为文档模型容易滥用——团队可能因为不想设计 Schema 而选择文档数据库，结果导致数据质量下降、数据集成困难、分析链路断裂。

图模型适合任意数据之间都可能相联的多对多关系。在 EDC 中，这对应的是关系密集型数据：反欺诈、社交网络、知识图谱、权限关系。这些数据的共同特征是关系比数据本身更重要，查询深度不可预测。EDC 对这类数据的供给方式是：作为专业服务提供，面向特定业务场景，不追求通用性。因为图数据库的运维复杂度和人才稀缺度都远高于关系型数据库，大面积推广不现实。

DDIA 把存储引擎分为两大类：日志结构，只允许附加到文件和删除过时的文件，不会更新已经写入的内容；面向页面，将磁盘视为一组可以覆写的固定大小的页面。

从 EDC 的视角看，这两类引擎对应两种截然不同的数据生命周期。

日志结构引擎（LSM-Tree 系）适合写密集、KV 访问、高吞吐的场景。在 EDC 中，这对应的是日志采集、消息存储、时序数据、用户行为追踪。这些数据的共同特征是写入量远大于读取量，读取通常是点查而非范围查询，数据有 TTL 或归档策略。LSM-Tree 把随机写入转化为顺序写入，代价是读放大和写放大。EDC 在容量规划时必须考虑：压缩策略对 I/O 的影响，读放大对查询延迟的影响，以及 compaction 对 CPU 和内存的消耗。这些不是理论问题，而是直接决定集群规模和成本的现实因素。

面向页面引擎（B+Tree 系）适合需要事务支持、范围查询、读多写少的场景。在 EDC 中，这对应的是核心交易系统。MySQL InnoDB 和 PostgreSQL 的默认引擎都是 B+Tree 系，这不是偶然——它们的目标场景正是 EDC 最核心的交易系统。B+Tree 的代价是页分裂和写放大，在高并发写入场景下锁竞争可能成为瓶颈。EDC 在选择 B+Tree 引擎时，必须评估写入并发量是否在引擎的舒适区内。

内存存储在 EDC 中分为两类：仅用于缓存的（如 Memcached），重启丢数据可接受；目标是持久性的（如 Redis 持久化模式），需要通过日志、快照或复制保证数据不丢。EDC 对内存数据库的规范是：如果数据丢了业务能自己恢复，那就是缓存；如果数据丢了业务无法恢复，那就必须配套持久化机制。不能把持久化责任推给“内存数据库”这个标签。

从 EDC 的视角看，数据仓库的定位不是“另一个数据库”，而是企业分析数据的集中存储和计算平台。它从各个 OLTP 系统抽取数据，转换成适合分析的模式，供分析人员使用。数据仓库包含公司各种 OLTP 系统中所有的只读数据副本。

列式存储在 EDC 中的价值在于：分析查询通常需要扫描大量记录但只涉及少数列，磁盘带宽而不是查找时间往往是瓶颈。ClickHouse、Doris、Snowflake 都是这个思路的产物。但它们都不适合做 OLTP，不要试图用同一套系统同时满足交易和分析需求。
