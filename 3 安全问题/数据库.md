数据库（EDC 手册版）

引言：EDC 看数据库的方式

EDC 不是为一个应用选数据库，而是为整个企业的数据资产设计一套供给体系。这意味着思考的起点不是“这个数据库有什么特性”，而是“企业里有哪些数据，这些数据要被谁用、怎么用、用多久、出了问题谁负责”。

从这个视角看，DDIA 里关于数据模型、存储引擎、复制、分区、事务的知识，不是用来做技术选型对比的，而是用来回答 EDC 面临的几个根本问题：

· 企业的数据应该分成几类？每类数据应该放在什么样的存储系统上？
· 这些存储系统之间如何复制、如何分区、如何保证一致性？
· 当业务增长、机房故障、人为变更发生时，这套体系如何保持可用和可维护？

EDC 手册的读者是平台工程师、数据架构师、DBA 和应用团队。它不需要解释 LSM-Tree 和 B+Tree 的内部机制，但需要让读者理解：为什么有些数据放在 MySQL 上，有些放在 HBase 上，有些放在 ClickHouse 上；为什么有些系统必须用可串行化隔离，有些可以用读已提交；为什么跨机房复制不能简单配成同步。

以下按照 DDIA 的主题顺序展开，但每一条都从 EDC 的实际决策场景出发。

一、数据模型：EDC 的数据分类与服务目录

EDC 面对的第一个现实是：企业里的数据不是一种，而是很多种。交易数据、配置数据、日志数据、关系数据、分析数据——它们的访问模式、一致性要求、生命周期完全不同。用一套数据模型承载所有数据，要么牺牲正确性，要么牺牲效率。

DDIA 把数据模型分为关系、文档、图三类。EDC 的视角不是比较这三者，而是把它们映射到企业的数据分类体系上。

关系模型适合多对一关系，强 Schema、频繁 Join。原因是二级索引、事务、外键约束成熟。在 EDC 中，这对应的是核心交易数据：订单、支付、账务、库存、客户主数据。这些数据的共同特征是正确性要求极高，业务规则频繁变化，需要 Schema 约束来保护数据质量。EDC 对这类数据的供给方式是：作为一级标准服务提供，统一版本、统一运维、统一备份恢复策略。不允许业务团队自建关系数据库，因为那会导致版本碎片化、备份策略不一致、安全策略不统一，最终在故障切换和审计时付出代价。

文档模型适合数据自包含、文档间关系稀少的场景。原因是嵌套存储，局部性好。在 EDC 中，这对应的是半结构化数据：内容管理、用户配置、商品详情、日志聚合。这些数据的共同特征是查询以单个文档为单位，跨文档关联少，Schema 灵活。EDC 对这类数据的供给方式是：作为可选服务提供，但必须有明确的使用场景审批。因为文档模型容易滥用——团队可能因为不想设计 Schema 而选择文档数据库，结果导致数据质量下降、数据集成困难、分析链路断裂。

图模型适合任意数据之间都可能相联的多对多关系。在 EDC 中，这对应的是关系密集型数据：反欺诈、社交网络、知识图谱、权限关系。这些数据的共同特征是关系比数据本身更重要，查询深度不可预测。EDC 对这类数据的供给方式是：作为专业服务提供，面向特定业务场景，不追求通用性。因为图数据库的运维复杂度和人才稀缺度都远高于关系型数据库，大面积推广不现实。

EDC 的数据模型治理原则只有一条：数据模型的选择是数据治理的起点。不同模型对应不同的数据质量保证方式、不同的集成方式、不同的生命周期管理方式。如果允许每个团队自由选择，结果必然是数据孤岛和治理成本失控。所以 EDC 必须建立数据模型的服务目录，明确每种模型的适用场景、接入流程、运维责任。

二、存储引擎：EDC 的存储服务分级

EDC 不需要向读者解释 LSM-Tree 和 B+Tree 的内部机制，但需要让读者理解：为什么有些数据放在 MySQL 上，有些放在 HBase 上，有些放在 ClickHouse 上。这背后的逻辑不是“哪个引擎更好”，而是“数据的访问模式决定了引擎的选择”。

DDIA 把存储引擎分为两大类：日志结构，只允许附加到文件和删除过时的文件，不会更新已经写入的内容；面向页面，将磁盘视为一组可以覆写的固定大小的页面。

从 EDC 的视角看，这两类引擎对应两种截然不同的数据生命周期。

日志结构引擎（LSM-Tree 系）适合写密集、KV 访问、高吞吐的场景。在 EDC 中，这对应的是日志采集、消息存储、时序数据、用户行为追踪。这些数据的共同特征是写入量远大于读取量，读取通常是点查而非范围查询，数据有 TTL 或归档策略。LSM-Tree 把随机写入转化为顺序写入，代价是读放大和写放大。EDC 在容量规划时必须考虑：压缩策略对 I/O 的影响，读放大对查询延迟的影响，以及 compaction 对 CPU 和内存的消耗。这些不是理论问题，而是直接决定集群规模和成本的现实因素。

面向页面引擎（B+Tree 系）适合需要事务支持、范围查询、读多写少的场景。在 EDC 中，这对应的是核心交易系统。MySQL InnoDB 和 PostgreSQL 的默认引擎都是 B+Tree 系，这不是偶然——它们的目标场景正是 EDC 最核心的交易系统。B+Tree 的代价是页分裂和写放大，在高并发写入场景下锁竞争可能成为瓶颈。EDC 在选择 B+Tree 引擎时，必须评估写入并发量是否在引擎的舒适区内。

哈希索引在 EDC 中的典型场景是缓存层、会话存储、高频更新的 KV 数据。这类场景的共同特征是访问模式是点查，不需要范围查询，每个键的值频繁更新。EDC 对缓存层的规范只有一条：缓存必须可重建，不存唯一数据。这是缓存和数据库的根本区别。如果一个数据只存在缓存里，那它就不是缓存，而是数据库——只是选错了存储引擎。

SSTable 的核心特性是把随机写入转化为顺序写入，代价是读取时可能需要检查多个 SSTable。EDC 需要理解这个权衡，因为它是存储选型的基本判断依据：写密集场景选 LSM-Tree 系引擎，读密集场景选 B+Tree 系引擎。

二级索引在 EDC 中的特殊之处在于分布式数据库中的索引分区问题。本地索引写入快但读取需要分散/收集，全局索引读取快但写入需要更新多个分区。这个权衡没有通用答案，取决于业务的读写比和延迟要求。EDC 的经验是：如果业务查询经常需要跨分区检索，全局索引虽然写入代价高，但读取体验更好；如果业务查询总是带分区键，本地索引更经济。

内存存储在 EDC 中分为两类：仅用于缓存的（如 Memcached），重启丢数据可接受；目标是持久性的（如 Redis 持久化模式），需要通过日志、快照或复制保证数据不丢。EDC 对内存数据库的规范是：如果数据丢了业务能自己恢复，那就是缓存；如果数据丢了业务无法恢复，那就必须配套持久化机制。不能把持久化责任推给“内存数据库”这个标签。

EDC 的存储服务分级思路是：一级存储（关系数据库）承载核心交易数据，二级存储（LSM-Tree）承载高写入数据，三级存储（列式）承载分析数据，四级存储（专业数据库）面向特定场景。这个分级的目的是让大部分数据落在标准化的存储服务上，降低运维复杂性，同时保留专业数据库的接入能力。

三、数据仓库：EDC 的分析数据基础设施

EDC 中 OLTP 和分析是两种完全不同的工作负载，必须用不同的系统承载。DDIA 对这个问题的表述是：OLTP 系统对业务运作很重要，通常要求高可用与低延迟，不愿意做影响事务性能的分析查询。数据仓库是一个独立的数据库，分析人员可以查询他们想要的内容而不影响 OLTP 操作。

从 EDC 的视角看，数据仓库的定位不是“另一个数据库”，而是企业分析数据的集中存储和计算平台。它从各个 OLTP 系统抽取数据，转换成适合分析的模式，供分析人员使用。数据仓库包含公司各种 OLTP 系统中所有的只读数据副本。

ETL 流程在 EDC 中不是简单的数据搬运，而是数据治理的关键环节。抽取、转换、加载——每一步都必须考虑：调度依赖、数据质量校验、血缘追踪、失败重试。最关键的约束是不能影响 OLTP 系统的性能。这意味着 ETL 必须从从库或快照读取，不能在主库上跑大查询。

列式存储在 EDC 中的价值在于：分析查询通常需要扫描大量记录但只涉及少数列，磁盘带宽而不是查找时间往往是瓶颈。ClickHouse、Doris、Snowflake 都是这个思路的产物。但它们都不适合做 OLTP，不要试图用同一套系统同时满足交易和分析需求。

EDC 的实践原则是：分析负载必须与生产负载资源隔离。这不仅是性能问题，也是可用性问题。一个失控的分析查询不应该拖垮交易系统。

四、数据编码与数据流：EDC 的数据交换标准

EDC 中存在多种数据流：数据库读写、RPC 调用、异步消息。每种数据流都涉及编码和解码，而编码格式的选择直接影响系统的兼容性、可演化性和运维复杂度。

DDIA 比较了几种编码格式：编程语言特定的编码仅限于单一语言，无法提供前向后向兼容；JSON、XML、CSV 等文本格式普遍但类型模糊；Thrift、Protobuf、Avro 等二进制模式驱动格式紧凑高效，有清晰的兼容性语义。

从 EDC 的视角看，编码格式的选择不是技术偏好，而是数据交换标准的制定。EDC 必须规定：内部 RPC 用什么格式，日志和事件用什么格式，禁止使用语言特定的序列化。Schema 必须注册，必须保证向前和向后兼容，每次 Schema 变更都必须经过兼容性检查。

数据流的几种模式在 EDC 中有不同的兼容性要求。数据库读写：写入进程编码，读取进程解码，Schema 演进必须保证旧数据可读。RPC 和 REST：客户端和服务端通常同时升级，兼容性窗口短。异步消息：发送者和接收者可能长期处于不同版本，兼容性窗口长。这就是为什么消息格式比 RPC 格式更需要严格的 Schema 管理。

EDC 的经验是：编码格式的兼容性不是编码格式本身决定的，而是使用方式决定的。同一个 JSON，如果写入方和读取方对字段含义的理解不一致，兼容性就会出问题。所以 Schema 注册和兼容性检查比格式选择更重要。

五、数据复制：EDC 的容灾与一致性架构

复制在 EDC 中的意义远不止“备份”。它关系到高可用、容灾、读扩展、就近接入等多个架构目标。DDIA 列出了复制的几个目的：高可用性、断开连接的操作、延迟、可伸缩性。

从 EDC 的视角看，复制策略的选择不是单个应用的技术决策，而是企业容灾架构的组成部分。EDC 必须回答：哪些数据需要跨机房复制？哪些需要跨 Region？复制延迟的容忍度是多少？故障切换时如何保证数据不丢？

DDIA 讨论了三种主要复制方法。单主复制：客户端将所有写入发送到单个节点（领导者），该节点将数据更改事件流发送到其他副本（追随者）。读取可以在任何副本上执行，但从追随者读取可能是陈旧的。多主复制：客户端发送每个写入到几个领导节点之一，任何一个都可以接受写入。领导者将数据更改事件流发送给彼此以及任何跟随者节点。无主复制：客户端发送每个写入到几个节点，并从多个节点并行读取，以检测和纠正具有陈旧数据的节点。

EDC 的默认选择是单主复制。单主复制简单、一致性好、冲突少。多主复制只在多数据中心主动-主动场景下考虑，而且必须配套冲突解决策略。无主复制适合高可用和多 DC 场景，但需要法定读写和冲突解决，运维复杂度高。

复制滞后会引起一些奇怪效应，DDIA 讨论了对应的一致性模型。写后读：用户应该总是看到自己提交的数据。单调读：用户在一个时间点看到数据后，不应该在某个更早的时间点看到数据。一致前缀读：用户应该将数据视为具有因果意义的状态。

从 EDC 的视角看，这些不是可选项。如果业务逻辑依赖这些一致性保证，就必须在架构层面实现它们，而不是期望数据库默认提供。写后读通过会话绑定或读主库来实现；单调读通过会话固定副本或一致性令牌来实现；一致前缀读通过相关操作落同一分区或因果一致性存储层来实现。

EDC 在多数据中心场景下的核心运维原则是：本地写入可用性优先。跨 DC 的复制延迟不能影响本地写入的成功率。客户端通常只等待来自其本地数据中心内的法定节点的确认，从而不会受到跨数据中心链路延迟和中断的影响。对其他数据中心的高延迟写入通常被配置为异步发生。同时必须监控复制延迟，超阈值告警，并评估是否影响业务一致性要求。

六、分区：EDC 的水平扩展策略

分区在 EDC 中的意义不是“数据库太大了要分”，而是数据量超过单机承载能力后的必然选择。DDIA 的表述是：数据量非常大的时候，在单台机器上存储和处理不再可行，而分区则十分必要。分区的目标是在多台机器上均匀分布数据和查询负载，避免出现热点。

从 EDC 的视角看，分区策略的选择直接决定了运维复杂度和扩展成本。分区通常与复制结合使用，使得每个分区的副本存储在多个节点上。一个节点有多个分区，如果使用主从复制模型，每个分区领导者被分配给一个节点，追随者被分配给其他节点。

DDIA 讨论了两种主要的分区方法。键范围分区：键是有序的，分区拥有从某个最小值到某个最大值的所有键。排序的优势在于可以进行有效的范围查询，但如果应用程序经常访问相邻的键，则存在热点的风险。当分区变得太大时，通常将分区分成两个子分区，动态地再平衡分区。散列分区：散列函数应用于每个键，分区拥有一定范围的散列。这种方法破坏了键的排序，使得范围查询效率低下，但可以更均匀地分配负载。通过散列进行分区时，通常先提前创建固定数量的分区，为每个节点分配多个分区，并在添加或删除节点时将整个分区从一个节点移动到另一个节点。

两种方法搭配使用也是可行的，例如使用复合主键：使用键的一部分来标识分区，而使用另一部分作为排序顺序。EDC 在时序数据场景中经常使用这种复合分区：按业务 ID 散列分片保证写入均匀，片内按时间排序保留范围查询能力。

二级索引的分区是 EDC 中特别容易出问题的环节。本地索引存储在与主键和值相同的分区中，写入时只有一个分区需要更新，但读取二级索引需要在所有分区之间进行分散/收集。全局索引存在不同的分区中，条目可以包括来自主键的所有分区的记录，写入时需要更新多个分区中的二级索引，但可以从单个分区中进行读取。EDC 的经验是：如果业务查询经常需要跨分区检索，全局索引虽然写入代价高，但读取体验更好；如果业务查询总是带分区键，本地索引更经济。

请求路由和服务发现是分区之后的必然问题。确定客户发出请求时，需要知道要连接哪个节点进行读取。常见实现是依赖一个独立的协调服务，比如 ZooKeeper 来跟踪集群元数据。每个节点在 ZooKeeper 中注册自己，ZooKeeper 维护分区到节点的可靠映射。只要分区分配发生了改变，或者集群中添加或删除了一个节点，ZooKeeper 就会通知路由层使路由信息保持最新状态。EDC 中 etcd 和 Consul 也承担类似角色。

七、事务：EDC 的数据一致性保障

在 EDC 中，事务不是一个可选的优化，而是核心交易系统的必需品。DDIA 对事务的定位是：事务是一个抽象层，允许应用程序假装某些并发问题和某些类型的硬件和软件故障不存在。各式各样的错误被简化为一种简单情况：事务中止，而应用需要的仅仅是重试。

从 EDC 的视角看，什么时候需要事务的判断标准是：如果业务操作涉及多个数据项的读写，或者依赖读取的值做决策再写入，就必须使用事务。支付、订单、库存、账务这些核心系统，没有事务是不可想象的。

DDIA 讨论了几个广泛使用的隔离级别：读已提交、快照隔离（有时称为可重复读）和可串行化。

竞争条件的例子在 EDC 中对应着具体的业务风险。脏读：一个客户端读取到另一个客户端尚未提交的写入。读已提交或更强的隔离级别可以防止脏读。脏写：一个客户端覆盖写入了另一个客户端尚未提交的写入。几乎所有的事务实现都可以防止脏写。读取偏差：在同一个事务中，客户端在不同的时间点会看见数据库的不同状态。快照隔离经常用于解决这个问题。更新丢失：两个客户端同时执行读取-修改-写入序列，其中一个写操作覆盖了另一个写操作的结果。快照隔离的一些实现可以自动防止这种异常，而另一些实现则需要手动锁定。写偏差：一个事务读取一些东西，根据它所看到的值作出决定，并将该决定写入数据库，但写入时该决定的前提不再是真实的。只有可串行化的隔离才能防止这种异常。幻读：事务读取符合某些搜索条件的对象，另一个客户端进行写入，影响搜索结果。快照隔离可以防止直接的幻像读取，但是写入偏差上下文中的幻读需要特殊处理，例如索引范围锁定。

弱隔离级别可以防止其中一些异常情况，但要求应用程序开发人员手动处理剩余那些。只有可串行化的隔离才能防范所有这些问题。

DDIA 讨论了实现可串行化事务的三种不同方法。字面意义上的串行执行：如果每个事务的执行速度非常快，并且事务吞吐量足够低，足以在单个 CPU 核上处理，这是一个简单而有效的选择。两阶段锁定：数十年来一直是实现可串行化的标准方式，但是许多应用出于性能问题的考虑避免使用它。可串行化快照隔离：一个相当新的算法，避免了先前方法的大部分缺点。它使用乐观的方法，允许事务执行而无需阻塞。当一个事务想要提交时，它会进行检查，如果执行不可串行化，事务就会被中止。

EDC 的实践建议是：支付扣款场景必须使用可串行化隔离级别；评论列表、商品详情这类场景可以使用读已提交。各数据库产品的默认隔离级别和实际行为必须建立对照表，因为同样叫可串行化，不同产品的实际保证可能不同。更重要的是，应用程序开发人员必须理解自己所使用的隔离级别能防止什么、不能防止什么，而不是假设数据库会解决所有并发问题。

EDC 中一个常见的误区是：认为使用了事务就万事大吉。实际上，事务的隔离级别决定了它能防止哪些异常。如果应用依赖可串行化，但数据库默认是读已提交，那么应用必须显式设置隔离级别，或者使用锁定机制来弥补。这个责任不能推给数据库，必须由应用架构师在设计中明确。
